# fletcher-arrow-bridge

Server-side bridge between `fletcher-core`'s wire format and Apache Arrow C++.
Provides four components in one static library:

- **`Codec`** (`fletcher/arrow_bridge/codec.hpp`) — binds an `arrow::Schema` to
  `EncodeRow` / `DecodeRow` over the positional wire format. `EncodeRow` writes
  straight into a `WriteBuffer` (the overload the vector-returning `EncodeRow`
  wraps), or returns the bytes in a fresh `EncodedRow`; `DecodeRow` goes the
  other way, building one `arrow::Scalar` per field. Before writing a byte,
  `EncodeRow` checks each value's Arrow type against the schema field's type
  with `DataType::Equals`, so a mismatch (a `timestamp[ns]` value into a
  `timestamp[ms]` field, `list<int32>` into a `list<int64>` field) throws
  `std::invalid_argument` instead of silently desynchronising the decoder on
  the next field. Wire-compatible with the positional encoders generated by
  `fletcher-protoc` for edge code, so bytes produced on an embedded device
  decode cleanly here.
- **`BatchDecoder`** (`fletcher/arrow_bridge/batch_decoder.hpp`) — decodes
  positional wire rows straight into Arrow builders instead of one `Scalar`
  per cell; the batched (RecordBatch) subscriber's decode path. See
  [BatchDecoder](#batchdecoder) below.
- **`ArrowRowView` / `ArrowScalarList` / `ArrowNestedList`**
  (`fletcher/arrow_bridge/arrow_row_view.hpp`) — zero-copy template accessors for
  generated row-view classes.
- **CRS utilities** (`fletcher/arrow_bridge/crs_utils.hpp`) — EPSG → PROJJSON resolution
  and Arrow extension-metadata helpers for geometry fields.

## BatchDecoder

`Codec::DecodeRow` builds one `arrow::Scalar` per field per row — the right
shape for an `ArrowRow`, but wasted work for a batched subscriber that only
wants a `RecordBatch` at the end. `BatchDecoder` decodes each wire row
straight into one `arrow::ArrayBuilder` tree matching the schema, field for
field, so no per-cell `arrow::Scalar` is ever created:

```cpp
#include <fletcher/arrow_bridge/batch_decoder.hpp>

fletcher::BatchDecoder decoder(schema);
decoder.Reserve(expected_rows);
for (...) decoder.Append(row_data, row_len);
std::shared_ptr<arrow::RecordBatch> batch = decoder.Finish();  // resets for reuse
```

Use it when you're accumulating rows into a `RecordBatch` and can build one
`BatchDecoder` per subscription up front; stay with `Codec::DecodeRow` for a
one-row-at-a-time `ArrowRow`, or when the schema is one `BatchDecoder` can't
build (see below) — `DecodeRow` supports strictly more schemas.

`Append` is two-pass: it validates the whole row before writing anything to a
builder, so a malformed row throws `std::invalid_argument` and leaves nothing
appended — the batch already in progress is unaffected. A row that is
well-formed but would overflow a 32-bit Arrow offset (a utf8/binary, list,
map, or dense-union column near 2 GiB) throws `fletcher::BatchCapacityExceeded`
instead, also with nothing appended; `Finish()` the batch and `Append()` the
same row again. A `std::runtime_error` means an internal failure
(allocation) — the pending rows are undefined at that point, so `Finish()`
and discard the batch rather than trusting it.

The constructor rejects a schema it cannot build into columns: null,
extension, decimal32/64, run-end-encoded, and list-view types; a dictionary
nested below the top level; and a dictionary whose value type is nested or
`float16`. `Codec::DecodeRow` still handles every one of those. A top-level
dictionary column *is* supported — the wire carries only the value type (see
[Dictionary Types](../docs/wire-format-specification.md#dictionary-types)),
and `Finish()` re-folds the accumulated values into a `DictionaryArray` of
the field's declared type on the way out.

An all-valid run of a fixed-width element type (numeric, temporal, interval,
decimal, `fixed_size_binary`, or `bool`) inside a list is appended with one
memcpy rather than one builder call per element — the same optimization
`Codec::EncodeRow`/`DecodeRow` make for list and map bodies.

Not thread-safe: one `BatchDecoder` per subscription.

## Building locally

Requires [Conan 2](https://docs.conan.io/2/) and CMake 3.15+.

### Windows

```bash
conan create . -pr:a=../.conan-profiles/Windows-msvc194-x86_64-Release -o "&:run_tests=True"
```

### Linux (devcontainer)

See the repo root's [Development environment](../README.md#development-environment) section for how to open the devcontainer (VS Code or manual Docker). Once inside, from this directory:

```bash
conan create . --build=missing -pr:a=../.conan-profiles/Linux-gcc13-x86_64-Release -o "&:run_tests=True"
```

## Consuming the package

```python
def requirements(self):
    self.requires("fletcher-arrow-bridge/0.5.0-alpha")
```

```cmake
find_package(fletcher-arrow-bridge CONFIG REQUIRED)
target_link_libraries(my-target PRIVATE fletcher::arrow-bridge)
```

```cpp
#include <fletcher/arrow_bridge/codec.hpp>
#include <fletcher/arrow_bridge/crs_utils.hpp>
```

`arrow-bridge` re-exports its dependencies (`fletcher-core`,
`arrow::arrow`) transitively, so consumers don't need to declare them
separately.

### Measured decisions (2026-09-02)

Numbers from `benchmarks/bench_arrow_codec`, the same machine (i9-13950HX, MSVC 19.44, Release),
run twice back to back with nothing else compiling, comparing commit `564467b` against the tree with
`BatchDecoder`, the `PositionalWriter` encoder and the fixed-width run path. Medians; per row at
N = 8000 for the batched arms. The full 128-arm table, run logs and lockfiles are described in
[`benchmarks/README.md`](benchmarks/README.md).

| Row shape | Batched decode: `DecodeRow` + `AppendScalar` → `BatchDecoder` | Allocations per row | Encode: `EncodeRow` → into the provider buffer |
|---|---|---|---|
| 10 flat scalars | 1.23 µs → 0.160 µs (7.7×) | 15 → 0.08 | 170 ns → 108 ns (1.6×), 1 → 0 |
| Pose: 2 nested `list<double>` (16 + 6) | 9.52 µs → 0.130 µs (73×) | 94 → 0.08 | 2.33 µs → 234 ns (10×), 27 → 2 |
| Cloud: 2 × `list<float>` ×2667 | 566 µs → 4.44 µs (127×) | 5364 → 0.05 | 575 µs → 4.64 µs (124×), 5347 → 2 |
| Points: `list<struct<x,y,z>>` ×1000 | 5.46 ms → 57.4 µs (95×) | 54 087 → 0.06 | 607 µs → 81 µs (7.5×), 8015 → 4 |
| Nested: `list<list<struct>>`, map, struct² | 130 µs → 0.84 µs (155×) | 1269 → 0.20 | 8.58 µs → 1.44 µs (6×), 116 → 7 |
| Generic: dictionary, FSL, decimal, union, `list<timestamp>` | 223 µs → 1.60 µs (139×) | 2056 → 0.16 | 106 µs → 1.33 µs (80×), 1015 → 2 |

Why each of the three moves paid: one memcpy for an all-valid fixed-width list run instead of a
builder call per element (2667 floats: 4.0 µs → 0.62 µs, 6.5×); no `arrow::Scalar` per cell on the
batched path (the allocation column); the encoder walking typed arrays instead of `GetScalar` per
list element (the encode column, Cloud and Generic). The per-row `Codec::DecodeRow` API keeps its
shape and gains only where a run can be bulk-copied (Cloud 8.6 → 2.0 µs, Generic 96.6 → 2.2 µs; flat
rows unchanged). The generic encoder stays 10–35× behind the schema-specialised code
`fletcher-protoc` generates — that is the cost of dispatching on `arrow::Type` per field at run time,
and every producer in the tree publishes through the generated `EncodeTo` anyway.

End to end on the planner bridge (real Fast DDS, batched `SubscriberArrow`, 60 000 points per
frame at 10 Hz): 79 % → 4 % of a core, 1.39 → 0.26 ms per row, 0 drops. Wire bytes unchanged,
pinned by `EncodeMatchesPositionalWriter_*` in `tests/test_codec.cpp`.

## CI pipeline

`.github/workflows/ci.arrow-bridge.yml` is `workflow_call`-only;
it runs `build-windows` + `build-linux` and is invoked from `ci.pr.yml`
on PRs touching `arrow-bridge/**` and from `cd.arrow-bridge.yml`
on `arrow-bridge-v*` tag pushes. The `upload` job that creates the
GitHub Release lives in `cd.arrow-bridge.yml`.
