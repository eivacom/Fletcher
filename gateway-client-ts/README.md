# @eiva/fletcher-gateway-client

[![npm (scoped)](https://img.shields.io/npm/v/@eiva/fletcher-gateway-client?label=latest)](https://www.npmjs.com/package/@eiva/fletcher-gateway-client)
[![npm (scoped with tag)](https://img.shields.io/npm/v/@eiva/fletcher-gateway-client/alpha?label=alpha)](https://www.npmjs.com/package/@eiva/fletcher-gateway-client)

TypeScript client for the Fletcher WebGateway — WebSocket transport with positional row codec.

## Installation

```bash
# latest stable
npm install @eiva/fletcher-gateway-client

# latest alpha
npm install @eiva/fletcher-gateway-client@alpha
```

## Building from source

The build toolchain (pinned Node.js + npm) lives in the repo's devcontainer at
[`.devcontainer/`](../.devcontainer), so the client builds the same way locally and in CI.
In VS Code, *Reopen in Container*; for a plain Docker shell see
[CONTRIBUTING.md](../CONTRIBUTING.md#development-environment). Inside the container:

```bash
cd gateway-client-ts
npm ci         # clean install from package-lock.json
npm run build  # tsc -> dist/
npm test       # vitest run
```

`ci.gateway-client` runs these exact steps inside the shared devcontainer image.

## Usage

Use the same MAJOR.MINOR of this client and of the code generator (`@eiva/protoc-gen-fletcher`):
the generated publisher and subscriber call this client's API, so code generated by plugin 0.6
needs client 0.6.

**With generated code** (recommended). For this `positions.proto`:

```proto
syntax = "proto3";
package positions;
import "google/protobuf/empty.proto";

message Position { double x = 1; double y = 2; }

service Positions { rpc Report(stream Position) returns (google.protobuf.Empty); }
```

`protoc-gen-fletcher` with `--fletcher_opt=ts` writes `positions.fletcher.ts`, with a publisher
and a subscriber that carry the topic (`positions/Positions/Report`) and the schema, typed by the
message ([`protoc/README.md`](../protoc/README.md#options)):

```ts
import { FletcherClient } from '@eiva/fletcher-gateway-client';
import { Positions_ReportPublisher, Positions_ReportSubscriber } from './positions.fletcher.js';

const client = new FletcherClient({
  url: 'ws://localhost:9090',
  onError: (fault) => console.warn(fault.reason, fault.error),
});
await client.connect();

// Declares the topic with the message's full schema.
const publisher = await Positions_ReportPublisher.create(client);
await publisher.publish({ x: 1.0, y: 2.0 });

const subscriber = new Positions_ReportSubscriber(client);
const id = await subscriber.subscribe((row, attachments) => console.log(row.x, row.y));
await subscriber.unsubscribe(id);

client.close();
```

**By hand**, with a schema written out field by field. Name the row type on `subscribe`, since
a plain `SchemaDescriptor` does not carry it:

```ts
import { FletcherClient, WireTypeId } from '@eiva/fletcher-gateway-client';
import type { SchemaDescriptor } from '@eiva/fletcher-gateway-client';

interface Position {
  x: number;
  y: number;
}

const client = new FletcherClient({ url: 'ws://localhost:9090' });
await client.connect();

const schema: SchemaDescriptor = {
  fields: [
    { name: 'x', fieldNumber: 1, wireType: WireTypeId.FLOAT64, nullable: false },
    { name: 'y', fieldNumber: 2, wireType: WireTypeId.FLOAT64, nullable: false },
  ],
};

// Publish
await client.createTopic('position', schema);
await client.publish('position', schema, { x: 1.0, y: 2.0 });

// Subscribe
await client.subscribe<Position>('position', schema, (row, attachments) => {
  console.log(row.x, row.y);
});

// List topics
const topics = await client.listTopics();

client.close();
```

## API

### `FletcherClient`

| Member | Description |
|---|---|
| `connect()` | Open the WebSocket connection |
| `createTopic(topic, schema?)` | Create a topic, optionally announcing its schema |
| `subscribe(topic, schema, callback)` | Subscribe to a topic |
| `subscribeBatched(topic, schema, callback, options?)` | Subscribe, receiving rows in windows (below) |
| `unsubscribe(subId)` | End a subscription: its callback is not called again from this call on, whatever the gateway replies; a batched one delivers its pending window first |
| `publish(topic, schema, data, attachments?)` | Publish a row to a topic |
| `listTopics()` | List all topics on the gateway |
| `close()` | Close the connection; batched subscriptions deliver their pending windows first |
| `undecodableRows` | Property: how many rows did not decode against their subscription's schema and were dropped |

A subscription's callback never breaks the connection. When it throws, when the promise of an
`async` callback rejects, or when a row sent to it does not decode, the client calls the
`onError` option with the reason (`'HandlerThrew'` or `'RowUndecodable'`), the subscription ID
and the error, and goes on with the next row. Without `onError` the fault is written to
`console.error`.

**Batched delivery.** `subscribeBatched` gathers rows into windows and calls
`callback(rows, attachments, status)` once per window, with row `i`'s attachments at index `i`.
A window is delivered:

- when it holds `options.maxRows` rows (default 8000; below 1 means 1), with `status.reason`
  `'RowLimit'`;
- when its deadline passes, with `'Timeout'`. The deadline is armed by the window's first row
  (or undecodable row) and falls `options.timeoutMs` (default 60000, `Infinity` for never) after
  the previous window, so a steady stream gets a window every `timeoutMs` and a row after a
  longer quiet spell is delivered at once;
- when the subscription ends through `unsubscribe`, `close` or the connection closing, with
  `'Closing'`.

A row that does not decode is reported through `onError`, left out, and counted in the window's
`status.rowsDropped`; a window of only such rows is delivered empty. A negative or `NaN`
`timeoutMs`, a `NaN` `maxRows`, and a `timeoutMs` above `MAX_BATCH_TIMEOUT_MS` (2^31-1 ms, about
24.8 days, the longest `setTimeout` waits) are refused before anything is sent. Browsers throttle
timers in hidden tabs, so there a `'Timeout'` window can come late; it is never lost.

These are the rules of the C# gateway client's `SubscribeBatchedAsync` and of the native
`SubscriberArrow`, with three differences: a window holds decoded rows, not an Arrow
`RecordBatch`, and `maxRows` counts the rows delivered (C# counts the rows received, an
undecodable one included); there is no byte ceiling on a window; and the longest finite timeout
is 24.8 days (C#: 49.7).

**What `publish` refuses.** `publish` (and `encodePositional`) throws, and sends nothing, when a
field the schema marks not nullable is `null` or absent while its parent is present. In the
generated schemas that is every field except an `optional` one (proto3 or proto2) and a wrapper
type such as `google.protobuf.Int32Value`, so a repeated field must be `[]` and a map field
`new Map()`, never left out. The message names the field by its path, as the C++ codecs and
the C# gateway client do: `s.x` for a struct's field, `readings[].x` for a field of a list
element, `tags{}.value.x` for one of a map value. It also refuses a `null` or `undefined` map
key. The C++ codecs and the C# gateway client refuse the same rows, because a C++ row class has
nowhere to put the null. A null list element or map value is accepted, as the native schema
marks those nullable.

### `FletcherClientOptions`

| Option | Type | Default | Description |
|---|---|---|---|
| `url` | `string` | — | WebSocket URL, e.g. `ws://localhost:9090` |
| `backend` | `'object' \| 'arrow'` | `'object'` | Decode backend; `'arrow'` is not implemented yet, and the constructor refuses it |
| `onError` | `(fault) => void` | `console.error` | Called when a subscription's callback throws or its promise rejects, or a row does not decode |

The client does not reconnect, as the C# gateway client does not: when the connection closes,
pending requests reject, batched subscriptions deliver their pending windows as `'Closing'`, and
every subscription ends. Connect again and subscribe again to resume. The `reconnectDelay` option
of earlier versions is still accepted and ignored.
